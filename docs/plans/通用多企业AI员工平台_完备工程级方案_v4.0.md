# 通用多企业 AI 员工平台：完备工程级方案 v4.0

日期：2026-07-25

状态：P0—P2 通用产品建设；P3 目标企业接入

阶段审批人：外部产品所有者

## 1. 执行结论

项目改为先建设可复用产品，再接入具体企业：

> P0—P2 不需要提供任何目标企业内部资料，只使用合成数据完成产品核心、打包、安全和生产加固；P3 才一次性接收企业接入包，创建 Tenant，导入真实用户与知识，并逐级连接企业系统。

这个路线同时解决两个目标：

1. 当前不等待企业资料和跨部门协调，直接推进系统建设；
2. 产品核心不绑定一家企业，可以打包交付给不同企业。

当前用户的角色固定为“外部产品所有者”，是 P0—P3 唯一阶段审批人，不被建模为目标企业员工。产品所有者是否把材料发给其他部门、向谁征求意见，由产品所有者自行决定；本项目只记录最终审批结果。

## 2. 四阶段路线

| 阶段 | 目标 | 数据边界 | 主要交付 | 退出条件 |
|---|---|---|---|---|
| P0 | 产品边界与技术基线 | 仅合成数据和公开背景 | 领域模型、架构、租户边界、契约、威胁模型、阶段门 | 技术证据齐全，产品所有者批准 |
| P1 | 通用多租户核心建设 | 仅合成租户、用户、知识、流程 | 个人 AI、身份、权限、知识、Skills、模型、审计核心 | 合成功能与隔离验收通过，产品所有者批准 |
| P2 | 产品化、打包与生产加固 | 仍仅使用合成数据 | 安装包、配置、升级回滚、HA/DR、压测、沙箱、Connector Templates | 预生产验收通过，产品所有者批准 |
| P3 | 目标企业接入与验收 | 经授权的真实企业数据 | Tenant、真实用户与知识、Connector Instances、真实试点和上线 | 企业验收包通过，产品所有者批准 |

P0—P2 不以员工人数作为阶段定义，也不要求 20—50 名真实员工试用。真实员工、真实资料和真实业务结果全部属于 P3。

## 3. 角色与审批

### 3.1 外部产品所有者

- 决定产品方向和阶段范围；
- 审批 P0、P1、P2、P3 的冻结验收包；
- 是项目看板唯一可改变阶段状态的人；
- 不因为这个角色成为目标企业员工；
- 不因为阶段审批自动获得企业数据库、系统或个人数据访问权。

### 3.2 产品建设代理

AI/Codex 和后续工程人员负责方案、实现、测试、证据和交付，不拥有阶段审批权。

### 3.3 目标企业与 Enterprise Users

P3 前不选择或创建目标企业 Tenant，也不存在 Enterprise Users。P3 接入时，目标企业提供运行期身份、角色和权限配置；这是产品运行授权，不是项目阶段审批。

### 3.4 单一审批机制

每个阶段只产生一次产品所有者审批：

```text
产品建设与验证
→ 形成版本化验收包
→ 计算完整内容哈希
→ 外部产品所有者选择批准、排除、退回或暂缓
→ 批准后开放下一阶段
```

本项目不跟踪其他部门签字、意见流转或审批链。任何其他意见都由产品所有者吸收后，以最终审批结果体现。

## 4. 产品总体架构

```text
员工入口 / 管理门户
        ↓
AIOS Core
  ├─ Tenant Registry
  ├─ Identity Projection
  ├─ Authorization Service
  ├─ Personal State & Memory
  ├─ Knowledge & Retrieval
  ├─ Agent / Skill Registry
  ├─ Model Gateway
  ├─ Workflow & HumanDecision
  ├─ Audit & Usage
  └─ Sandbox Broker
        ↓
Connector Gateway
  ├─ Connector Templates（P0—P2）
  └─ Connector Instances（仅 P3）
```

推荐继续以 LibreChat 类项目作为可替换员工体验层，公司无关能力放在自建 AIOS Core。企业事实、权限、审批、审计和 Connector 状态不能只存在聊天产品数据库中。

## 5. 多企业产品化原则

### 5.1 核心代码不绑定企业

禁止在产品核心写死：

- 企业名称、Logo 或域名；
- 部门名称、岗位名称和工号规则；
- OA、ERP、BI 厂商或字段；
- 企业制度目录和知识分类；
- 企业审批流程、金额和业务规则；
- 企业模型供应商和部署地区。

企业差异通过 Tenant 配置、策略包、知识包、Skills、主题和 Connector Instance 表达。

### 5.2 Tenant 强隔离

每个 Tenant 独立控制：

- 用户与组织投影；
- 角色、关系和权限策略；
- 知识、向量索引和文件；
- 个人会话与记忆；
- Agent、Skill 和工具版本；
- 模型路由、预算和配额；
- 密钥引用和 Connector Instances；
- 审计、导出和保留策略。

任何请求都必须先解析 `tenant_id + principal_id`，再执行权限决策。浏览器提交的姓名、邮箱、角色或 Tenant ID 不能直接作为授权依据。

### 5.3 配置优先，不 Fork

新企业接入默认只增加：

- Tenant 配置；
- 身份映射；
- 策略和角色；
- 知识与 Skills；
- Connector Instances；
- 主题和品牌配置。

只有可复用、与企业无关的能力才进入产品核心。

## 6. P0—P2 数据规则

P0—P2 唯一允许：

- 完全虚构的企业和组织；
- 合成用户和身份生命周期；
- 合成制度、产品资料和业务案例；
- 合成 OA、ERP、BI 响应；
- 合成审批、审计和异常；
- 不来自真实企业的压测数据。

以下内容即使脱敏也推迟到 P3：

- 企业内部制度、产品和流程；
- 真实员工、部门、客户、供应商；
- 真实订单、合同、KPI 和经营数据；
- 企业 IdP、网络、服务器和系统字段；
- 企业导出快照和历史数据库。

阶段门只要发现 P0—P2 存在企业内部资料、企业用户、凭据、企业网络访问或 Connector 大于 C0，就返回 `BLOCKED`。

## 7. P3 前的公开企业信息

可以提前收集或由产品所有者提供：

- 官方网站公开介绍；
- 公开工商登记、年报和新闻；
- 公开产品目录、招聘信息和公开联系方式；
- 公开行业与监管资料。

这些信息标记为 `PUBLIC_EXTERNAL_CONTEXT`，保留来源、发布日期和采集日期。它只能用于研究、行业模板和接入准备，不能：

- 当作企业内部权威事实；
- 创建 Tenant 用户或权限；
- 判断真实订单、库存、审批或 KPI；
- 激活 Connector；
- 推断未公开的商业或个人信息。

## 8. 身份与权限

P1/P2 使用产品自有的合成身份服务验证：

- 多 Tenant 登录隔离；
- 稳定 `principal_id`；
- 短时断言；
- 调岗、停用和撤权；
- 会话撤销；
- 重放阻断；
- 管理员最小权限。

P3 再绑定企业 IdP 或项目专用身份源。企业 IdP 的 `{issuer, sub}` 映射到产品内部稳定身份，不以邮箱或姓名作为长期安全主键。

权限至少分为：

1. 平台管理权限；
2. 知识访问权限；
3. 工具和 Connector 权限；
4. 代码执行权限；
5. 正式动作与批准权限。

产品所有者的项目阶段审批权不自动转换为 Tenant 内的上述权限。

## 9. 知识、Skills 和个人 AI

P1 使用合成知识包验证：

- 文档版本、生效和失效；
- 来源引用；
- Tenant、部门、项目和个人 ACL；
- 冲突版本与撤回；
- 提示词攻击和越权拒绝；
- Skills 的版本、测试、发布、灰度和回滚。

个人记忆只保存用户偏好和明确确认的工作状态，不保存企业价格、订单、合同、认证、KPI 等权威事实。

P3 再导入目标企业批准的真实知识包和 Skills。

## 10. Connector 产品模型

### 10.1 Connector Template

P0—P2 只建设通用契约和 Mock Adapter：

- `operation_id` 和 `contract_version`；
- 输入输出 Schema；
- 权限与用途；
- 来源、版本和新鲜度；
- 错误分类、超时和重试；
- 幂等、回读和补偿接口；
- 观测、审计和停用开关。

Connector Template 不包含企业 URL、账号、Token、字段映射或网络访问。

### 10.2 Connector Instance

仅在 P3 为一个 Tenant 创建。每个实例依次经过：

| 阶段 | 含义 |
|---|---|
| C0 | 禁用，无凭据、无企业网络 |
| C1 | 经授权的快照或文件 |
| C2 | 正式只读接口 |
| C3 | 受控写回 |

不能跳级。阶段状态、证据和回滚相互独立，不因某个企业可用而自动复制给其他 Tenant。

## 11. 代码执行沙箱

P1 默认不开放任意代码，只验证固定转换器。P2 才完成产品级沙箱：

- 按任务创建短生命周期 microVM；
- 不与其他 Tenant 共享可写状态；
- 默认无任意网络；
- 无宿主机、Docker Socket、长期密钥和企业数据区访问；
- CPU、内存、时间、进程、文件和输出限制；
- 镜像签名、依赖锁定、销毁和审计；
- 通过越权、逃逸、DoS、出口和恢复测试。

P3 按 Tenant 和岗位单独决定是否启用。

## 12. 打包与部署

P2 形成可交付产品包，至少包括：

- 容器或 Helm 部署清单；
- 环境变量和密钥引用模板；
- 数据库迁移和回滚；
- Tenant 初始化工具；
- 管理门户和只读审计；
- 合成演示 Tenant；
- 健康检查、日志、指标和告警；
- 备份恢复和升级说明；
- SBOM、固定镜像摘要和许可证清单；
- Connector Template SDK 和 Mock 服务。

默认安装必须是空产品，不含任何真实企业资料、账号、网络地址或 Connector Instance。

## 13. P3 企业接入包

进入 P3 后，目标企业的授权接入人通过正式渠道提供以下接入包；外部产品所有者只审批项目阶段结果：

1. 企业与 Tenant 基本信息及接入授权记录；
2. 用户、组织、角色、登录和撤权来源；
3. 内部知识、版本、权限、有效期和首批 Skills；
4. 数据分级、上云、隐私、保留、删除和审计规则；
5. 企业系统、接口、测试环境、字段、新鲜度和回滚规则；
6. 一个主场景、3—5 个任务、案例、人工基线和成功指标。

生产密码、Token、私钥和连接串不进入文档或聊天，只由授权人员写入密钥管理系统。

首次把 Connector Instance 从 C0 升到 C1 时，必须绑定企业接入授权引用和冻结接入包的 SHA-256 哈希；这是一项接入前置证据，不是本项目要跟踪的企业内部审批流程。

## 14. 阶段验收

### P0

- 领域词汇、P0—P3 边界和单一审批模型已冻结；
- P0—P2 零企业内部数据门禁可执行；
- Tenant、身份、权限、知识、Skills、Connector、审计和沙箱契约明确；
- 威胁模型和验收测试已评审；
- 产品所有者批准 P0。

### P1

- 至少三个合成 Tenant；
- 跨 Tenant、跨用户、跨角色泄露为零；
- 合成身份、知识、Skills、模型和审计主路径可用；
- 撤权和拒绝路径可复现；
- 产品所有者批准 P1。

### P2

- 产品包可重复安装、升级和回滚；
- 2 倍目标峰值压测、恢复演练和关键告警通过；
- microVM 沙箱和 Connector Templates 通过安全测试；
- 依赖、许可证、SBOM、备份和运行手册齐全；
- 产品所有者批准 P2。

### P3

- 企业接入包完整且可追溯；
- Tenant 隔离、真实身份、知识和权限验收通过；
- Connector Instances 按 C0—C3 独立验收；
- 真实任务质量、效率、安全、恢复和成本达到冻结基线；
- 产品所有者批准 P3。

## 15. 当前立即执行

当前不等待任何企业资料，直接继续：

1. 完成 P0 通用领域模型和阶段门；
2. 冻结 Tenant、Principal、Knowledge、Skill、Connector 和 Audit 契约；
3. 建立多合成 Tenant 测试数据生成器；
4. 完成身份、权限和零企业数据 PoC；
5. 选择可替换员工入口并验证 AIOS Core 接口；
6. 完成 P0 验收包，交外部产品所有者一次审批。

## 16. 可实现度

- P0 通用边界与技术基线：高；
- P1 多租户核心：高；
- P2 产品打包与生产加固：中高；
- P3 单个企业接入：中高，取决于该企业的身份、资料质量、接口和运行条件；
- 同一产品连续接入多家企业：中高，前提是坚持配置与 Connector Instance，而不是为每家企业 Fork 核心。

最大的工程风险不是模型，而是跨 Tenant 隔离、身份撤权、企业差异配置、知识版本、Connector 安全和可重复部署。新阶段设计把这些风险放在产品核心解决，而不是等接入一家企业后再返工。
